## Plan of Implementation
I’d implement the hybrid approach for **Reports → Fees**. Supabase supplies a bounded window of daily totals by batch. Week, Month, and Batch changes within that window filter and regroup those totals in the browser. The selected period still defines **which receipts** are included, and Outstanding Balance still means **what remains unpaid today** on those receipts. A December clearance can therefore change November’s outstanding total. Annotation 1

1. **Benchmark the current screen first.** On an authenticated production build, measure initial load, previous-week and previous-month clicks, and the time until the charts are ready. Break out Supabase query time, TypeScript aggregation time, and response size. Then compare three-, six-, and twelve-month windows. I’d start with three months and choose six or twelve if the measured cost is close. The existing query retrieves receipts first, then looks up students and linked clearances in chunks, so a small browser payload alone tells us little about the cost. I haven’t measured authenticated load times yet. [Current Fees query](</D:/DEVELOPMENT/SOFTWARES/SPORTS/Pro Badminton/src/lib/queries/fees-report.ts:30>)

2. **Keep reads on the server and aggregate in TypeScript.** Seed the initial window from the Reports page. Use an authenticated `GET` route handler for later windows, background refreshes, and exact-period exports. Both entry points use the same server-only query and pure aggregation, with stable pagination past Supabase’s default 1,000-row limit. Return summaries in integer paise and scope every read by academy. I verified the live policies: **Owner and Manager** are the two roles that can read both receipts and batches, so I’d use that access rule for the live Fees segment and its export. [Next.js route handlers](https://nextjs.org/docs/app/getting-started/route-handlers) · [Supabase pagination](https://supabase.com/docs/reference/javascript/select)

3. **Commit the period, charts, and export selection together.** Reuse the Dashboard’s IST period calculation. A period is a cache hit only when its full calendar span fits inside the window, including a Monday-to-Sunday week that crosses a month boundary. Track the covered calendar span separately from the date through which data was fetched, so future dates remain empty. On a cache miss, keep the previous label and charts visible, show **Loading [requested period]** beside the navigator, and temporarily disable period navigation and export. Cancel superseded requests and reject late responses. On failure, retain the last successful view and offer Retry.

4. **Refresh the loaded window as a unit.** Keep the cache in memory while Reports is mounted. A fresh route entry loads a fresh server window. Returning to Fees within Reports or refocusing the browser can show the existing view immediately and refresh it in the background. This covers payments recorded on other pages without relying on `revalidatePath` to clear browser state. On focus, recalculate today in IST and refresh if the date rolled over. If the user was viewing the current period, follow the new period across a week or month boundary. Keep an explicitly selected historical period pinned. Show **Data refreshed at … IST** using the successful server response timestamp.

5. **Fetch fresh data for each export.** Capture the displayed period and batch when the user clicks CSV or PDF, then fetch that exact period from the server. Include the scope and data timestamp in the file so it’s clear why a fresh export could differ from a screen loaded earlier. Open the print window during the PDF click so browser popup handling still works. If the fresh read fails, show an error and leave the export ungenerated.

6. **Verify the behavior and compare timings.** Check that in-window navigation sends zero data requests in the usual case. Test be­yond-window navigation, boundary weeks, reversed response order, failed refreshes, and an IST midnight rollover. Use a receipt cleared in a later month to verify that refreshing an older period updates its remaining balance while cash stays attributed to the payment dates. Check that exports use the clicked filters and fresh values even if the screen started from cached data.

The plan uses the existing schema. Historical period-end balances stay a separate reporting decision. No files were changed in this planning turn.


## Result 
Implemented the **Fees hybrid cache**. Supabase remains the source of truth. The browser keeps three calendar months of server-calculated totals in memory, including boundary weeks, so covered Week, Month, and Batch changes make no data request.

When a period needs a fetch, the navigator shows what’s loading while the previous period and charts stay visible. The new period, charts, and export selection update together. Superseded requests are ignored, and a failed request leaves the last successful view available with Retry.

The report shows when its data was refreshed, checks for stale data and IST date rollover on focus, and refreshes the loaded window when returning to Fees. A later clearance can therefore update an older receipt’s outstanding balance. **Every CSV and PDF export fetches fresh data for the displayed period and batch.**

The production build, changed-file lint, [Fees regression checks](</D:/DEVELOPMENT/SOFTWARES/SPORTS/Pro Badminton/scripts/verify-fees-report.mjs>), and production authentication smoke test passed. Repository-wide lint still reports the same 59 errors and 27 warnings. The browser runtime couldn’t start, so signed-in visual checks and end-to-end timings remain unverified. I kept the initial window at three months pending that benchmark.
